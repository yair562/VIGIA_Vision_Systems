# VIGIA Vision Systems

## 07 — Cronograma Maestro

**Estado:** Activo  
**Versión:** 1.0  
**Fecha de inicio:** 09 de septiembre de 2026  
**Fecha límite:** 16 de diciembre de 2026  
**Metodología:** Scrum  
**Modelo:** Desarrollo paralelo por dominios + integración progresiva  
**Pregunta Central:** *¿Cuándo trabajará cada equipo, qué hitos deben alcanzarse en cada iteración y cómo se protegen los plazos de entrega?*  
**Propósito:** Transformar el Roadmap de capacidades de VIGIA en un plan temporal detallado y sincronizado, coordinando los 9 Workstreams sin dependencias bloqueantes mediante desarrollo paralelo, integraciones progresivas y una regla estricta de protección de entrega.

# 4. Principio de Trabajo Paralelo y Desacoplamiento

La presencia de una actividad en un periodo **no significa que las demás actividades deban esperar**.

Las dependencias entre dominios son administradas mediante mecanismos de desacoplamiento técnico:
* **Contratos de Interfaces:** Firmas y estructuras de datos congeladas.
* **APIs tipadas:** Protocolos REST y endpoints definidos con esquemas.
* **Protocolos de comunicación serial:** Tramas binarias o ASCII documentadas con checksums.
* **Datos simulados (*Fixtures*):** Lotes de fotogramas y payloads JSON estáticos.
* **Mocks y Stubs:** Servidores simulados que devuelven respuestas de acuerdo con el contrato.
* **Simuladores de Hardware:** Scripts locales que emulan el comportamiento del microcontrolador.
* **Hardware de prueba en banco:** Prototipos de escritorio para validar firmware de forma aislada.
* **Pruebas automatizadas de contrato:** Validación continua de que ninguna parte altera la interfaz.

### Ejemplo de Desacoplamiento Operativo:
```text
Frontend
   │
   └──► Mock API
            │
            ▼
        Dashboard
```
Mientras Backend desarrolla en paralelo:
```text
Backend
   │
   └──► API Real
```
Posteriormente, la integración ocurre sin fricción:
```text
Mock API ──► API Real ──► Integración Validada
```
El mismo principio aplica exactamente a IA, Hardware, Data y demás dominios.

# 6. Criterio de Avance

> **Regla de Oro:**  
> Una actividad **NO** se considerará completada únicamente porque su código exista en el repositorio.

Toda actividad, capacidad o entregable debe contar con:
1. **Implementación:** Código o circuito funcional.
2. **Prueba:** Test unitario, de integración o validación en banco.
3. **Integración:** Enlace verificado con los módulos dependientes cuando corresponda.
4. **Evidencia:** Logs estructurados, grabaciones, métricas o fotogramas.
5. **Documentación:** Explicación técnica clara y actualizada.
6. **Criterio de Aceptación Cumplido:** Aprobación formal contra la *Definition of Done*.

# 7. Regla de Protección del Deadline (16 de Diciembre)

El **16 de diciembre de 2026** constituye la fecha límite absoluta e inamovible del proyecto. Para proteger la entrega y garantizar la máxima estabilidad, se establece un calendario estricto de cierre:

### 06 de Diciembre — Release Candidate (RC) Técnico
* El sistema completo debe ser esencialmente funcional en todas sus capacidades previstas.
* Todas las integraciones principales (A a E) deben estar operando.

### 07 al 13 de Diciembre — Estabilización y Blindaje
* Periodo exclusivo de estabilización.
* Se prohíbe el desarrollo de nuevas características.
* Prioridad absoluta: corrección de errores (*bugs*), afinación de pruebas, consolidación de evidencias, revisión de manuales y ensayos de demostración.

### 13 de Diciembre — Feature Freeze
* **Congelamiento total de funcionalidades.**
* No se admite la incorporación de ningún cambio de alcance ni funcionalidad adicional, salvo parches de seguridad críticos.

### 14 al 16 de Diciembre — Cierre, Empaquetado y Entrega
* No se planifica desarrollo ordinario.
* Actividades exclusivas de entrega:
  * Empaquetado final y verificación de instaladores / imágenes edge.
  * Respaldos definitivos de código, datos y firmware.
  * Ensayo general de la presentación física y digital.
  * Demostración oficial ante evaluadores y entrega formal del proyecto.
